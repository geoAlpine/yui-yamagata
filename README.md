# やまがた結（ゆい）

災害のときに、開いてる店・給水所・通れる道の「今」を、見た人が報告し合う。
山形県向けに運用しているが、**都道府県コードを差し替えれば他県でも動く**
（[他の都道府県で使う](#他の都道府県で使う)）。

**名前について**: 「結（ゆい）」は農村の相互扶助の慣行。
住民同士が報告し合って支え合うという、このサイトの仕組みそのものを指す。
読みが割れる字なので、画面では常に「やまがた結（ゆい）」と読み仮名を添える
（災害時に口頭で伝わることが生命線のため）。

稼働中: **https://yui-yamagata.com**
運営: geoAlpine合同会社 / ライセンス: **Apache License 2.0**

設計の全体像と判断の根拠は **[DESIGN.md](./DESIGN.md)** を参照。
コミットメッセージにも「なぜそうしたか」を残してあるので、`git log` が設計資料を兼ねる。

## 動かす

前提: Node 22+ / PostgreSQL 17+ with PostGIS（ローカルは Postgres.app）

```bash
# 1. DBを用意
createdb bousai
psql -d bousai -f db/001_schema.sql
for f in db/0*.sql; do psql -d bousai -f "$f"; done

# 開発用のダミーデータ（★本番には流さない。db/dev/README.md 参照）
psql -d bousai -f db/dev/002_seed_dev.sql
psql -d bousai -f db/dev/003_seed_observations_dev.sql

# 2. 接続先と鍵
cat > .env.local <<'ENV'
DATABASE_URL=postgresql://<user>@localhost:5432/bousai
TOKEN_SECRET=dev-only-insecure-secret   # 本番では十分に長いランダム文字列にする（必須）
ADMIN_PASSWORD=devpass                  # 管理画面 /admin のパスワード
ENV

# 3. 起動
npm install
npm run dev            # http://localhost:3000
```

### 災害が起きたとき

**[docs/disaster-runbook.md](./docs/disaster-runbook.md) を最初に開く。**
緊張下で手順を思い出さなくて済むよう、やることだけを順に書いてある。
末尾にステージングでのリハーサル手順があるので、**災害が来る前に一度通しておく**。

### モードの切り替え

自動切替はしない（誤爆時の信頼失墜が回復不能なため）。DBを直接更新する。

```sql
UPDATE site_state SET mode = 'disaster';  -- 有事
UPDATE site_state SET mode = 'standby';   -- 平時（そなえ）
```

平時は避難場所・給水所など「先に知っておく」ものだけを出す。
営業状況のように平時に意味がないものは、そもそも一覧に出さない。
平常時の営業時間や混雑はGoogleのほうが正確なので、そこは張り合わずに送り出す。

## ブランチとデプロイ

```
stg  ブランチ → CI → staging.yui-yamagata.com （Basic認証・noindex）
main ブランチ → CI → yui-yamagata.com
```

CIが落ちたらデプロイは走らない。デプロイ後に200が返らなければ**自動で前の版に戻す**。
災害情報サイトでは「常に最新」より「常に動く」が優先。

`stg` で確かめてから `main` に入れる。とくに**災害モードへの切り替えは
本番でリハーサルできない**ので、ステージングで練習しておく。

例外として、ドキュメントだけの変更は `main` へ直接入れてよい。
本番の挙動を変えないため。`app/` `lib/` `db/` `deploy/` に触るものは必ず `stg` を通す。

### 検索と「自宅」

- **検索**: 名前・住所の部分一致（pg_trgm）。GETフォームなのでJSが落ちても動く。
  6,699件に増え、距離順に50件めくるより名前で引くほうが速い場面が増えたため。
- **自宅の登録**: 距離順は既定で現在地からだが、**発災時に自宅にいるとは限らない**。
  職場から自宅周辺の状況を見たい、家族のいる地域を確認したい、という使い方が現実的。
  端末内にのみ保存し、サーバには送らない。

### 中核となる3つの考え方

**1. 「投稿一覧」ではなく「場所に観測が積み重なる」**

同じ店に何人が報告しても1つのカードにまとまり、状況の推移が履歴として残る。
平時にスポットを登録しておけば、有事は「状態を選ぶだけ」で報告が終わる。

**2. 鮮度がすべて**

カテゴリごとにTTLを持つ（ガソリンの待ち時間120分／店舗営業360分／断水1440分）。
経過時間で3段階に減衰し、TTLを超えたら状態を「不明」に戻す。
判定は必ず `observed_at`（実際に見た時刻）で行い、`created_at`（投稿時刻）とは分ける。

**3. 登録は求めない。ただしIDは作らせない**

ユーザー登録なし。サーバがHMAC署名した匿名IDをHttpOnly cookieで配る。
localStorageのUUIDを信じると「100人が同意」を捏造できてしまうため。
プリミティブは2つだけ（spots←observations / notices）。3つ目は作らない。

## UI の方針

- **絵文字は使わない。** 端末ごとに描画が変わり、色もサイズも揃わないうえ、
  災害情報の画面では軽く見える。カテゴリは短い日本語のバッジ、
  下部タブは currentColor に従うインラインSVGで示す。
- **ダークテーマは持たない。** `color-scheme: light` を宣言し、
  端末がダークモードでも常に明るい画面を出す。
- 配色は全てWCAG AA（4.5:1）以上を実測で確認済み。

## 実データの取り込み

```bash
node --env-file=.env.local scripts/import_osm.mjs --dry   # 件数だけ確認
node --env-file=.env.local scripts/import_osm.mjs         # 取り込み
node --env-file=.env.local scripts/assign_municipality.mjs # 市町村を割り当て

# 住民拠点SS（停電時も給油できる自家発電付きスタンド）
#   資源エネルギー庁のページから最新の一覧(Excel)を落とし、
#   山形県の行だけを CSV で保存してから通す
node --env-file=.env.local scripts/import_juminss.mjs data/juminss_yamagata.csv --dry
```

現在の取り込み実績: **6,699件 / 市町村つき100% / 住所つき100%**
（避難場所・避難所 3,876 ＋ OSM由来 2,795 ＋ 応急給水拠点ほか）

**再実行は安全。** spots は `(osm_type, osm_id)` で upsert する。
消して作り直してはいけない（`observations` が `ON DELETE CASCADE` で連鎖削除され、
住民の報告が消える）。

`assign_municipality.mjs` は途中で止まっても続きから流せる。
Overpass の公開インスタンスは混雑時に 429/504 を返すため、一発で終わる前提に立たない。

### 避難場所と避難所は別物

国土地理院のデータから取り込んでいる。**2種類を混同してはいけない。**

| | |
|---|---|
| 指定緊急避難場所 | 発災時に**緊急で逃げる**場所。**災害種別ごとに指定**される |
| 指定避難所 | 災害後に**滞在する**場所 |

山形県内 2,727件の緊急避難場所のうち、**洪水に対応するのは1,035件だけ**。
地震向けに指定された場所へ豪雨時に逃げても意味がない。
`spots.hazards` に種別を保持し、カードに必ず表示する。

災害種別は**管理者が設定でき、利用者が上書きできる**。
管理者だけに頼ると、当日に設定を忘れたときや運営者自身が被災したときに
洪水非対応の避難場所が混ざったまま出続ける。逆に利用者に毎回選ばせると
被災地で操作が増えて使われない。両方持たせる。
URLに載るので「洪水の避難場所はここ」とリンクを共有できる。

また「指定されている」と「今開いている」も別物。
公式が言えるのは前者だけで、後者は住民の目撃が先行する。そこが本サイトの持ち場。


## 他の都道府県で使う

**このコードは山形県専用ではない。** 元にしているデータは全国共通で、
差し替えるのは実質2箇所（都道府県コードと表示名）。

災害が起きてから作り始めても間に合わない。平時に動かせる状態にしておくことに意味がある。

### 1. 都道府県コードを変える

| ファイル | 箇所 | 内容 |
|---|---|---|
| `scripts/import_shelters.mjs` | `const PREF = '06'` | JIS都道府県コード（2桁）|
| `scripts/import_osm.mjs` | `area["ISO3166-2"="JP-06"]` | ISO 3166-2 コード |

コードは全国分ある（01=北海道 … 06=山形 … 13=東京 … 47=沖縄）。
この2つを変えれば、**指定緊急避難場所・指定避難所と、店舗・施設の位置が
その県のぶんだけ入る。** 国土地理院もOpenStreetMapも全国を同じ形式で
公開しているので、コード以外に手を入れる必要はない。

```bash
node --env-file=.env.local scripts/import_shelters.mjs --dry   # 件数だけ見る
node --env-file=.env.local scripts/import_shelters.mjs
node --env-file=.env.local scripts/import_osm.mjs
node --env-file=.env.local scripts/assign_municipality.mjs
node --env-file=.env.local scripts/fill_addresses.mjs          # 町名を埋める
```

### 2. 名前とドメインを変える

| ファイル | 箇所 |
|---|---|
| `lib/seo.ts` | `SITE_NAME` |
| `lib/env.ts` | `PRODUCTION_URL` |
| `app/page.tsx` | 「公式情報はこちら」のリンク先（**その県の防災ページに差し替える**）|
| `app/about/page.tsx` | 運営者・連絡先 |

**公式情報へのリンクは必ず差し替えること。** 別の県の防災ページに
送るのは、災害時にいちばんやってはいけない類の誤りになる。

### 3. 県固有のデータ（任意）

`scripts/import_water.mjs`（応急給水拠点）と `import_juminss.mjs`（住民拠点SS）は
山形県の公開形式に合わせてある。他県では取得元が異なるので、
そのまま動くとは限らない。無くても本体は動く。

### 変えなくてよいもの

カテゴリ定義・TTL・鮮度判定・匿名ID・写真の扱いは、どの県でも同じ。
`lib/categories.ts` の TTL は「ガソリンの待ち時間は2時間で腐る」といった
情報の性質から決めており、地域差の話ではない。

### 相談

うまくいかない点は [Issues](https://github.com/geoAlpine/yui-yamagata/issues) へ。
自分の県で動かした、という報告も歓迎します。

### 取り込まないもの

`amenity=drinking_water`（常設の水飲み場）は取り込まない。
断水すれば水飲み場も止まるため、「給水所」として出すとかえって誤解を招く。
給水所は自治体の応急給水拠点と利用者の報告に任せる。

### 取り込みで踏んだ落とし穴

- **再開判定を「その市町村のスポットが既にあるか」にしてはいけない。**
  OSMの `addr:city` が付いていた分だけで処理済みに見え、山形市・鶴岡市など
  大きな市がまるごと飛ばされる。`import_progress` に処理そのものを記録する。
- **OSMの給油所名はブランド名だけのことが多い**（「エネオス」80件・「JA」30件）。
  283件中240件が同名なので、住民拠点SSの名寄せは名前だけでは決まらない。
  国土地理院の住所検索で座標を出して最寄りに当てている。
- **国土地理院の住所検索は、解決できない住所に市区町村の代表点を黙って返す。**
  `title` が「山形県山形市」のように市レベルで止まっていたら捨てる。
  捨てないと無関係な給油所が「自家発電あり」と表示され、停電時に人を無駄足させる。

## 写真

行列や貼り紙の1枚が持つ説得力は大きい。イマココナビにも無かった機能。

**容量より先に片付けるべきことが2つあった。**

1. **EXIFに撮影場所が入る。** スマホの写真にはGPS座標・端末情報・撮影時刻が
   埋まっており、そのまま上げると投稿者の居場所が公開される。匿名投稿の意味がなくなる。
   → クライアントで canvas に再描画して落とす（縮小・WebP化のついで）
2. **顔とナンバープレート。** 技術では消せないので、投稿前に警告し、
   事後に通報・削除できるようにする。

容量は問題にならない。長辺1280px・WebPで1枚150KB程度、1週間の災害で0.7GB。
VPSの空きは89GB。ただし**14日で自動削除**する。
2時間で腐る情報に付いた写真は翌日には価値がなく、
消すことが容量対策であると同時にプライバシー対策でもある。

### スマホの写真はそのままでは使えない

実機で起きること。いずれも `lib/photo.ts` で対処している。

| | 症状 |
|---|---|
| **EXIFの回転情報** | 縦で撮った写真が**横倒しになる**。`imageOrientation: 'from-image'` を明示する（既定挙動はブラウザ差がある） |
| **WebP非対応の端末** | 古いSafariは `canvas.toBlob(..., 'image/webp')` に対応せず、**エラーにならず黙ってPNGを返す**。150KBのはずが数MBになり上限で弾かれる。出来上がったBlobの `type` を確かめ、駄目ならJPEGにする |
| **HEIC** | iOSの標準形式。ファイル選択は通常JPEGに変換するが常にではない。読めなかったら黙らずに理由を返す |

写真は**アプリのツリーの外**（`/var/www/yui-uploads/{env}/`）に置く。
中に置くと nginx（www-data）が親ディレクトリを通れず403になり、
権限を緩めるとアプリのソースまで読ませることになる。
`ProtectSystem=strict` を使っているので、systemd の `ReadWritePaths` に
明示的に足す必要がある。

サーバに画像処理ライブラリは入れていない。依存が増えるうえ、
災害時のCPUを画像変換に使いたくない。
形式は中身（`RIFF..WEBP` / `FF D8 FF`）で検査し、WebPとJPEGだけ受ける。
配信はnginxが直接行い、Next.jsを通さない。

## 残っている課題

- **物資配布（`supply`）にデータ源がない。** 発災後に決まるのでOSMにも無い。
  自動で取るなら L-Alert（災害情報共有システム）が本命だが、受信には
  情報伝達者としての登録が要る。**都道府県は発信者側**なので、相談先はそこ。
  取れれば避難所の開設状況も公式情報として入る。副産物のほうが大きい。
- **災害ごみ仮置場（`waste`）は、実は平時に決まっている。**
  環境省の指針により市町村は災害廃棄物処理計画で**候補地を事前に選定**している。
  自動収集の問題ではなく、自治体から候補地リストをもらう話。避難所を
  国土地理院から取り込んでいるのと同じ扱いにできる。
  → 35市町村のサイトをスクレイピングする案は採らない。書式が不統一で、
    災害時には相手のサーバも不安定になる。運用が破綻する側の解。
- **バックアップが無い。** 定期取得の仕組みそのものが未整備。サーバを失うと
  住民の報告は復旧できない（参照データは外部から取り直せる）。

### アクセス集中への備え（対処済み・残りあり）

熊本地震のイマココナビは7万人/日を捌いた。同規模を単一VPSで受けるのは無理で、
しかも商用サイトが同居しているので**巻き添えが本当の risk**。

対処したもの:

- HTML（`/` `/notices` `/spots/:id`）… CDNで30秒キャッシュ＋SWR 120秒。
  何万人が見ても origin への到達は1URLあたり30秒に1回（`next.config.ts`）
- `GET /api/spots` … 同上。位置情報を許可した人の閲覧ごとに来ていた経路で、
  HTMLを載せたあとはここが最大だった。呼び出し側が**座標を約100mに丸めて**
  送るのでキャッシュが効く（丸めないとURLが利用者ごとに別物になる）
- 資源上限 … `CPUQuota=150%` / `MemoryMax=768M` / DB接続 `max: 8`。
  **近隣を巻き込む前に自分が先に落ちる**ように意図的に絞ってある

- 報告の導線（`/report` `/report/:spotId`）… 同上。報告する人が必ず通る2画面

### 実測値（2026-08-07 / VPS上から localhost:3010 へ）

CDNを外した**素の origin の性能**。同時5〜80まで上げて**失敗ゼロ**。

| 経路 | 上限 req/s | 平均遅延（同時40） |
|---|---|---|
| `GET /api/spots`（JSON 18.8KB） | 約550 | 76ms |
| `/spots/:id`（HTML） | 約180 | 224ms |
| `/report`（HTML） | 約115 | 348ms |

**律速はCPUではなくDB接続プール。** `/api/spots` は同時10以降 550 req/s で
頭打ちになるが load は 1.34（4コア中）。1クエリ約15ms・プール `max: 8` なので
`8 ÷ 0.015 ≈ 533 req/s` と計算が合う。意図的に絞った値がそのまま上限に出ている。

7万人/日・ピーク時が日量の2割なら平均 3.9 req/s、瞬間10倍でも 40 req/s。
**CDNが無くても読み取りは捌ける。** 「単一VPSでは持たない」は読み取りに関しては
杞憂だった。CDNを入れた現在は桁が違う。

なお CDN 経由の試験は測定にならない。1ページ約79KB で、こちらの回線が
先に飽和する（実測 17.6Mbps で頭打ち）。

残っているもの:

- **書き込み経路。** 報告・追認・写真はCDNで肩代わりできず、必ず origin まで来る。
  ただし閲覧に比べれば桁が違うので、詰まるとしても読み取りより後。
  なお画像処理はサーバでしていない（クライアントが縮小・EXIF除去・サムネ生成まで
  済ませて送る）。残るのは帯域とディスクI/O
**origin のIP露出は 2026-08-07 に塞いだ。** SPF レコードでIPが公開されており、
Host ヘッダを付けるだけで CDN を迂回できていた。上の対策は**CDNを通ってくる
相手にしか効かない**ので、塞ぐまでは実質「知っている相手には無防備」だった。
nginx の `location /` で Cloudflare 以外を 403 にしている
（`deploy/apply-origin-lockdown.sh`。firewall では同居サイトを巻き込むため使えない）。

`db/dev/` のシードは**概算の仮データ**であり、実在店舗の正確な位置ではない。
本番には流さない（`db/0*.sql` のグロブに入らないよう別ディレクトリにしてある）。
